# Улучшение алгоритма поиска траекторий перелёта

## Дата внесения изменений
10 июля 2026

## Описание проблемы

До внесения изменений алгоритм поиска оптимальной траектории имел следующие ограничения:

1. **На этапе сканирования сетки**: Для каждой точки (departure time, travel time) вычислялась только одна ветвь решения Ламберта (short-way или long-way), определяемая автоматически на основе геометрии.

2. **На этапе уточнения (Nelder-Mead simplex)**: Метод `RefineBestTransfer()` фиксировал флаг `longWay` из начального решения сетки и использовал только эту ветвь для всех последующих вычислений.

3. **Риск пропуска лучшего решения**: Если автоматический выбор ветви на грубой сетке указывал на менее оптимальную траекторию, алгоритм никогда не проверял альтернативу.

## Внесённые изменения

### 1. Добавлен метод `CalculateBestTransfer()` (PorkchopCalculator.cs:154-226)

```csharp
private static TransferDetails? CalculateBestTransfer(...)
```

**Назначение:**
- Если пользователь явно указал `longWay` (true/false), вычисляется только указанная ветвь
- Если `longWay == null` (автоматический режим), вычисляются обе ветви Ламберта
- Возвращается решение с минимальным суммарным ΔV

**Архитектура:**
- Использует `List<TransferDetails>` для сбора кандидатов
- Применяет LINQ для выбора: `.OrderBy(t => t.DVTotal).FirstOrDefault()`
- Легко расширяется для добавления multi-revolution траекторий

### 2. Обновлено сканирование сетки (PorkchopCalculator.cs:77-95)

**Было:**
```csharp
transfer = TransferCalculator.CalculateTransfer(..., request.LongWay);
```

**Стало:**
```csharp
transfer = CalculateBestTransfer(..., request.LongWay);
```

**Результат:** Каждая точка сетки теперь проверяет обе ветви (в автоматическом режиме).

### 3. Исправлен метод `RefineBestTransfer()` (PorkchopCalculator.cs:228-345)

**Удалено:**
```csharp
var longWay = seed.LongWay;  // Фиксация ветви из начального решения
```

**Изменено:**
```csharp
double Cost(double dep, double tt)
{
    var t = CalculateBestTransfer(..., request.LongWay);  // Проверяет обе ветви
    return t?.DVTotal ?? double.MaxValue;
}
```

**Результат:** Симплекс-метод может динамически выбирать лучшую ветвь на каждой итерации.

### 4. Добавлена финальная проверка (PorkchopCalculator.cs:330-343)

После завершения симплекса делается финальный вызов `CalculateBestTransfer()` для найденной точки, гарантируя возврат лучшего из обоих решений.

## Результаты тестирования

### Тестовая конфигурация
- **Маршрут:** Earth → Mars
- **Окно вылета:** 2026-08-01 до 2027-02-01
- **Время перелёта:** 120-360 дней
- **Сетка:** 48×48 (2304 точки)

### Результаты

| Режим | Long-way | Total ΔV | Дата вылета | Время перелёта |
|-------|----------|----------|-------------|----------------|
| `longWay: null` (авто) | Yes | **5766.4 m/s** | 2026-10-25 | 295 дней |
| `longWay: false` (явно) | No | 5868.8 m/s | 2026-11-12 | 272 дня |
| `longWay: true` (явно) | Yes | **5766.4 m/s** | 2026-10-25 | 295 дней |

**Вывод:** В автоматическом режиме алгоритм выбрал long-way траекторию как более оптимальную. Экономия составила **102.4 m/s** по сравнению с short-way решением.

## Ограничения

⚠️ **Не гарантируется нахождение абсолютного глобального минимума.**  

Остаются другие факторы, которые могут привести к пропуску лучшего решения:
- Слишком грубая сетка (шаг между узлами)
- Локальные минимумы функции стоимости
- Ограничения метода Nelder-Mead (может сойтись к локальному минимуму)
- Минимум между узлами сетки, куда симплекс не попал

## Заключение

Внесённые изменения представляют собой **инженерное улучшение**, которое устраняет специфический недостаток алгоритма — зависимость финального результата от первоначального автоматического выбора ветви Ламберта. 

Алгоритм стал более **надёжным** и **корректным** в автоматическом режиме, при этом сохранив полную обратную совместимость и не требуя изменений в публичном API.

Изменения подготовили архитектуру для дальнейших улучшений (многоступенчатый поиск, multi-revolution траектории) без необходимости масштабного рефакторинга.
